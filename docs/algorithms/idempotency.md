# ORA — Idempotency Design

## Principle

Every business-critical mutation must be safe to retry.  
Retrying the same operation with the same idempotency key and same payload must produce the same logical outcome.

## Idempotency Key Format

```
{rideId}:{operation}:{actorId}:{clientNonce}

Examples:
  ride_abc123:create:uid_xyz:nonce_111
  ride_abc123:offer:drv_456:nonce_789
  ride_abc123:select:uid_xyz:nonce_555
  ride_abc123:cash_collected:drv_456:nonce_321
  ride_abc123:cancel:uid_xyz:nonce_234
```

`clientNonce` is a UUID generated by the client before the first attempt. It is reused on all retries.

## Durable Idempotency Record

Collection: `idempotencyRecords`

```json
{
  "idempotencyKey": "ride_abc123:offer:drv_456:nonce_789",
  "requestHash": "sha256(...)",
  "actorId": "drv_456",
  "operation": "RIDE_OFFER_CREATE",
  "resourceId": "ride_abc123",
  "status": "PENDING",
  "responseSnapshot": null,
  "createdAt": "2026-08-18T07:30:00Z",
  "expiresAt": "2026-08-25T07:30:00Z"
}
```

Redis may cache recent outcomes for latency, but it is not the only store for ride creation, assignment, payment, payout, refund, or wallet mutations.

## Server Behavior

```
1. Client sends request with header: Idempotency-Key: {key}
2. Server looks up durable `idempotencyRecords`
3. If no record exists:
   a. create a `PENDING` record with requestHash
   b. process the request
   c. persist final responseSnapshot and terminal status
4. If record exists and requestHash differs:
   a. reject with 409 IDEMPOTENCY_KEY_REUSED
5. If record exists and status = PENDING:
   a. return 202 Accepted or block briefly and replay final result
6. If record exists and status is terminal:
   a. replay the stored responseSnapshot
```

## Operations Requiring Idempotency Keys

| Operation | Idempotency Required | Reason |
|---|---|---|
| POST /rides | YES | Network timeout on ride create → double ride |
| POST /rides/{id}/offers | YES | Duplicate Accept/Counter must not create two live offers |
| POST /rides/{id}/offers/{offerId}/select | YES | Duplicate select must replay assignment, not double-assign |
| POST /rides/{id}/offers/{offerId}/withdraw | YES | Duplicate withdraw |
| POST /rides/{id}/cancel | YES | Cancel delivered twice |
| POST /payments | YES | Double charge / duplicate provider attempt |
| POST /payments/cash-collected | YES | Duplicate CASH_COLLECTED |
| POST /wallet/topup | YES | Double wallet credit |
| POST /payout | YES | Double payout |
| Payment provider callbacks | YES | Duplicate callback |
| PATCH /rides/{id}/status | YES (for critical states) | Start/End ride delivered twice |
| POST /location/update | NO | GPS updates are fire-and-forget |

## Duplicate / Conflict Behavior

- same key + same payload + prior success → replay stored success
- same key + same payload + prior conflict/business failure → replay stored failure
- same key + different payload → reject with `409 IDEMPOTENCY_KEY_REUSED`
- server succeeds but client times out → retry returns stored success
- request retries while original is still running → `202 Accepted` or delayed replay

## What Is NOT Idempotent (and why)

- `POST /pricing/estimate` — read-only, not a mutation, no key needed
- `GET /rides/{id}` — read-only
- `GET /drivers/nearby` — read-only

## Idempotency vs Exactly-Once Semantics

Idempotency does NOT guarantee exactly-once execution of the underlying operation.  
It guarantees exactly-once observable outcome.

The operation may run once or multiple times internally (e.g., transaction retry), but the response to the client is always the same.

The distinction matters for payment systems: Ora must combine durable idempotency records with PSP-side idempotency or provider-reference semantics so duplicate captures and duplicate ledger postings are prevented.
